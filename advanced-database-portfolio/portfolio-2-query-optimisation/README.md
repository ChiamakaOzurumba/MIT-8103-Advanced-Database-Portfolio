# Portfolio 2 - Query processing and optimisation
Run `python run_portfolio.py` from the repository root. The runner generates 60,000 initial enrolments and benchmarks the same class-list join before and after an index on enrolments(offering_id). The composite primary key begins with student_id, which does not directly serve this offering-first lookup as effectively.
See evidence/query-plans.txt, query-results.txt and performance.json for actual outputs and all 30 timings per phase. Five warm-ups precede each phase. Full result retrieval is included; equality is checked independently of row order. The measured result applies only to this synthetic local workload. Execution order, OS scheduling and caching affect timings. There is no controlled cold-cache measurement. Larger distributed deployments require independent load testing.
Indexing trades space and write maintenance for faster targeted retrieval. ANALYZE refreshes planner statistics after indexing. Additional indexes should follow actual query patterns rather than being added to every column.
