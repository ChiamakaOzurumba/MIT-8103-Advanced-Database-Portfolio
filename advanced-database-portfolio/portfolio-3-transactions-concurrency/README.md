# Portfolio 3 - Transactions and concurrency
The runnable experiment is in run_portfolio.py; the SQL outline is in transactions.sql. Actual outputs are saved in evidence/transactions.txt. A two-seat offering first receives one committed enrolment. An attempted deletion is rolled back. Connection A inserts the second enrolment without committing; connection B still sees one. B's attempt to start a write transaction fails while A owns the writer lock. After A commits, B retries, but the capacity trigger rejects the third student.
Atomicity: rollback reverses deletion. Consistency: keys, foreign keys and the insert capacity trigger enforce rules. Isolation: B cannot see A's uncommitted insert. Durability: SQLite commit persists the database, but crash durability is not separately tested here.
Without serialised checking and insertion, two requests might both observe one free seat and oversubscribe it. This implementation uses BEGIN IMMEDIATE and SQLite's single-writer rule plus a capacity trigger; it does not claim row-level locking. WAL permits readers alongside a writer. The test uses two real connections with deterministic overlapping transactions in one process.
