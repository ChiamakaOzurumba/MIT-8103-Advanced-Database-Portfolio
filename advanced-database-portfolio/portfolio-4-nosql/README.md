# Portfolio 4 - Persistent key-value NoSQL model
The Python standard-library dbm.dumb backend provides a real disk-backed key-value store. It is deliberately used instead of pretending a JSON file alone is a database. Keys follow student:<id>:preferences and values are JSON-encoded objects, for example language, notification channels and accessibility preferences. This is the same Campus Register case study.
The runnable implementation in run_portfolio.py inserts, reads, updates, closes/reopens and deletes records. See evidence/nosql.txt and profile-example.json. Variable preferences fit a flexible value; enrolments remain relational because referential integrity and capacity checks are essential.
Trade-offs: there are no SQL joins, built-in secondary indexes, distributed replication or automatic referential integrity. The backend is a teaching example, not a production multi-user service. Single-process access is assumed. A production deployment could use a managed key-value service with access controls and tested consistency semantics. This portfolio does not claim to have deployed one.
